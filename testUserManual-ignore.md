# Arcade Management System — User Manual (Installation + Operations)

## Purpose and audience

This manual explains what the Arcade Management System does, who uses it (by role), why responsibilities are separated, and how to install and run the application from a fresh copy of the project (for example, an unpacked ZIP on a new computer with a new database).

After reading this manual, you should be able to:

- Install and run the system from scratch (no `node_modules/`, no preexisting `.htaccess`).
- Configure the database connection safely (environment variables or local config).
- Log in and complete common tasks for each role: System Admin, Owner, HR, Employee.
- Plan user stories for this system and map them to roles and data flows.
- Capture and label screenshots that match each procedure.

**Related technical artifacts (source of truth):**

- Database schema (DDL): `sql/migrations/000_run_all.sql`
- Demo data: `sql/seeds/001_seed_sample.sql`
- Reset script (drop all tables): `sql/reset.sql`
- ERD (text): `erd.txt` (mirrored at `docs/erd.txt`)

## Quick start (demo)

Use this if you are grading/demoing and want a working environment quickly.

1. Create a MariaDB/MySQL database and user.
2. Import schema: run `sql/migrations/000_run_all.sql`.
3. Import demo data (optional): run `sql/seeds/001_seed_sample.sql`.
4. Serve the app (recommended dev option):

   ```bash
   php -S localhost:8080 -t public
   ```

5. Open:

   - Home: `http://localhost:8080/index.php`
   - Login: `http://localhost:8080/login.php`

If you loaded the seed file, the common password for all seed users is `password`, and example logins include:

- `admin@arcade.local` (sys_admin)
- `owner@arcade.local` (owner)
- `hr@arcade.local` (hr)
- `employee@arcade.local` (employee)

## System overview

### What problem this system solves

This application models a ticket-based arcade venue:

- Guests visit **departments** (play areas, gift shop, customer support).
- Value is tracked in an internal currency: **tickets**.
- Ticket movements are recorded in a ledger (`ticket_accounts`, `ticket_transactions`) so activity is auditable.

### The “ticket economy” at a glance

Key idea: there is a shared operating pool called **gift shop budget** (account kind `gift_shop_budget`).

- **Owner investment** increases the operating pool.
- **Play-area admissions** (when recorded) also increase the operating pool.
- **Play-area payouts** decrease the operating pool.
- **Gift shop stocking** decreases the operating pool by:

  \[
  \text{spend tickets} = \text{unit cost} \times \text{units added}
  \]

The system also tracks a cumulative inventory-spend audit account: `gift_shop_inventory_spend`.

### Architecture overview (how PHP and React fit together)

- The backend pages are plain PHP endpoints under `public/`.
- Each major dashboard page renders a React “island” (mount div with `data-react-page`) plus a plain HTML fallback.
- React dashboard bundles are generated by Vite into `public/assets/build/`.

You can run the system as:

- PHP-only (with prebuilt assets), or
- PHP + Node toolchain (rebuild React assets when you change `frontend/`).

## Roles, responsibilities, and entry URLs

After login (`public/login.php`), users are redirected by role.

**Important:** registrations require admin approval.

- New users are created with `pending_approval = 1`.
- They may appear “signed in” for the public home page, but cannot access dashboards until approved.

### System administrator (`sys_admin`)

**Primary page:** `public/admin_dashboard.php`

**Handles:**

- Approving or rejecting new registrations.
- Deleting existing (already-approved) accounts.

**Why this role exists:** identity onboarding is separated from daily operations.

### Owner (`owner`)

**Primary page:** `public/owner_dashboard.php`

**Handles:**

- Creating and editing departments.
- Adding owner investment to the operating pool.
- Transferring generated department tickets into the operating pool.

**Why:** financial and structural controls stay with ownership.

### HR (`hr`)

**Primary page:** `public/hr_dashboard.php`

**Handles:**

- Creating employee records for existing user accounts.
- Updating employee department assignment, wage, and status.
- Terminating employees.
- Adding manual shifts (and reviewing live shift history).
- Reviewing sick-day requests (approve/deny).

**Why:** HR owns personnel data and audit logs.

### Employee (`employee`)

**Primary page:** `public/employee_dashboard.php`

All employees use the same dashboard, but available actions depend on the employee’s assigned department type:

- `play_area`: open/close attendee sessions, record admissions and payouts.
- `gift_shop`: manage catalog items, stock changes, redeem items.
- `customer_support`: verify member claims (convert session wallets to member wallets).

**Why:** prevents a “super user” screen and keeps actions attributable to department/employee.

## Greenfield installation (ZIP, no node_modules, no .htaccess)

These steps assume:

- You received the project as a ZIP.
- There is no `node_modules/` folder.
- You do not have a `.htaccess` file setting environment variables.
- You have a fresh MariaDB/MySQL instance.

### 1) Prerequisites

- PHP 8.x recommended with extensions: `pdo_mysql`, `json`.
- MariaDB or MySQL (InnoDB + utf8mb4).
- Node.js LTS + npm (only if you will rebuild frontend assets).

### 2) Unzip and choose a web root strategy

This project’s “web root” is the `public/` folder.

You have three common options:

- **Option A (recommended for grading/local dev):** run PHP’s built-in server, pointing at `public/`.
- **Option B (Apache/Nginx):** set `DocumentRoot` (or `root`) to the `public/` directory.
- **Option C (shared hosting):** place the project inside your hosting space and browse directly to the `public/` path.

### 3) Create the database and user

Run these once (example names—adjust to your environment):

```sql
CREATE DATABASE arcade_db CHARACTER SET utf8mb4 COLLATE utf8mb4_unicode_ci;
CREATE USER 'arcade_user'@'%' IDENTIFIED BY 'arcade_password';
GRANT ALL PRIVILEGES ON arcade_db.* TO 'arcade_user'@'%';
FLUSH PRIVILEGES;
```

### 4) Configure DB connection (no .htaccess required)

Database config is loaded from `config/db.php` and resolves credentials in this order:

1. Environment variables: `DB_HOST`, `DB_NAME`, `DB_USER`, `DB_PASS`, `DB_PORT`
2. A legacy local file `/home/bpaudel2/DBPaudel.php` (only on the author’s environment)
3. Safe defaults (`localhost`, `root`, empty password, db `bpaudel2`)

On a new machine, you should use **environment variables**.

#### Option A — Export env vars in your shell (works well with PHP built-in server)

```bash
export DB_HOST=localhost
export DB_PORT=3306
export DB_NAME=arcade_db
export DB_USER=arcade_user
export DB_PASS='arcade_password'
```

Then run:

```bash
php -S localhost:8080 -t public
```

#### Option B — Set env vars in Apache/Nginx config (no .htaccess)

If your environment does not allow `.htaccess`, you can set env vars in the server config.

**Apache VirtualHost example (one common approach)**

> Note: this is an example. Exact paths/modules vary by distro and hosting environment.

```apache
<VirtualHost *:80>
   ServerName arcade.local

   DocumentRoot /absolute/path/to/387Project/public
   <Directory /absolute/path/to/387Project/public>
      Require all granted
      AllowOverride None
   </Directory>

   # Equivalent to what some deployments place in .htaccess
   SetEnv DB_HOST localhost
   SetEnv DB_PORT 3306
   SetEnv DB_NAME arcade_db
   SetEnv DB_USER arcade_user
   SetEnv DB_PASS arcade_password
</VirtualHost>
```

If your instructor/host expects `.htaccess`, you can still use it, but you must ensure the server allows it:

- Apache directory config must allow overrides (`AllowOverride All`), and
- the `mod_env` module must be enabled for `SetEnv`.

**Nginx + php-fpm notes**

- Set PHP environment variables in the php-fpm pool config (not in the Nginx server block).
- Serve the `public/` folder as the `root`.

Minimal Nginx server-block concept:

```nginx
server {
   listen 80;
   server_name arcade.local;
   root /absolute/path/to/387Project/public;
   index index.php;

   location / {
      try_files $uri $uri/ /index.php?$query_string;
   }

   location ~ \.php$ {
      include fastcgi_params;
      fastcgi_param SCRIPT_FILENAME $document_root$fastcgi_script_name;
      fastcgi_pass unix:/run/php/php8.2-fpm.sock;
   }
}
```

#### Option C — Edit `config/db.php` for local-only development

This is the simplest for a class demo, but avoid committing real credentials.

### 5) Import schema and (optional) demo seed

From the `mysql` or `mariadb` client:

```text
USE arcade_db;
SOURCE /absolute/path/to/sql/migrations/000_run_all.sql;
-- Optional demo data:
SOURCE /absolute/path/to/sql/seeds/001_seed_sample.sql;
```

To wipe and reinstall:

```text
SOURCE /absolute/path/to/sql/reset.sql;
SOURCE /absolute/path/to/sql/migrations/000_run_all.sql;
SOURCE /absolute/path/to/sql/seeds/001_seed_sample.sql;
```

### 6) Verify the DB connection

Once the app is served, open:

- `http://localhost:8080/index.php?db_test=1`

Expected output:

- `DB connection: OK`

### 7) Frontend build (only if you need to rebuild assets)

If your ZIP does not include `node_modules/` (typical), you can reinstall dependencies:

```bash
npm ci
```

Then build:

```bash
npm run build
```

Output goes to `public/assets/build/` and should include a Vite manifest at:

- `public/assets/build/.vite/manifest.json`

If you do not build, the app can still fall back to `public/assets/js/app.js` and `public/assets/css/app.css`.

## Planning user stories

Good user stories keep development aligned with:

- The role that needs the capability
- The business outcome
- Clear acceptance criteria

### Recommended format

- **As a** <role>,
- **I want** <capability>,
- **So that** <outcome>.

Add:

- Acceptance criteria (Given/When/Then)
- Data touchpoints (tables/flows)
- Out-of-scope notes

### Why role separation matters in this codebase

This application enforces separation of duties:

- Admin approves accounts (identity + provisioning).
- Owner controls budgets and departments.
- HR controls personnel records and attendance/sick approvals.
- Employees execute operational actions tied to a department.

This prevents accidental privilege escalation and keeps the audit trail meaningful.

### Example user stories (starter set)

1) **Account approval**

- As a sys_admin, I want to approve registrations so that only authorized staff can access dashboards.
- Acceptance: pending users cannot access dashboards; approved users can.

2) **Owner investment**

- As an owner, I want to add operating tickets so that play areas and procurement can continue.
- Acceptance: budget increases; ledger entry created.

3) **Gift shop stocking debit**

- As a gift shop employee, I want stocking to subtract unit cost × units added so that inventory purchasing is accounted for.
- Acceptance: increasing stock reduces budget and increases inventory-spend ledger.

4) **Sick-day review**

- As HR, I want to approve/deny sick requests so that weekly hours reflect approved paid sick days.
- Acceptance: approved requests add 8 hours per day in HR weekly totals.

## Troubleshooting

### “DB connection: ERROR” on the smoke test

- Confirm the database exists and you used the correct name.
- Confirm the user has privileges.
- Confirm env vars are set in the same shell/session where PHP runs.
- If using Apache/Nginx without `.htaccess`, confirm the env vars are configured in the server.

### Blank dashboard / missing styling

- Build assets: `npm ci` then `npm run build`.
- Confirm `public/assets/build/.vite/manifest.json` exists.
- If you cannot build, confirm `public/assets/js/app.js` and `public/assets/css/app.css` exist for fallback.

### “Account pending approval”

- Ask sys_admin to approve the registration in the Admin Dashboard.

### “Your employee profile has not been set up yet”

- HR must create an `employees` record linked to your user email, or sys_admin approval must have created it.
